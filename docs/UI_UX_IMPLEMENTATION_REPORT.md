# تقرير تنفيذ تحسينات واجهة وتجربة المستخدم

## نظام الدولية للموارد البشرية — ElDawliya HRMS

**تاريخ التقرير:** 19 أغسطس 2026  
**النطاق:** واجهة نظام Django، نظام التصميم، لوحة التحكم، ووحدة الإجازات  
**حالة التنفيذ:** تحسينات أساسية ومتكاملة منفذة؛ فحص Django الشامل يحتاج اعتماداً بيئياً إضافياً موضحاً أدناه.

---

## الملخص التنفيذي

تمت مراجعة النسخة الأحدث من المستودع ودمج العمل عليها بصورة تحفظ التغييرات الحديثة الموجودة بالفعل بدلاً من استبدالها. يعالج التنفيذ تشتت الواجهة في الطبقة الأساسية عبر النظام الموحد الموجود، ويضيف تحسيناً فعلياً قابلاً للاستخدام في وحدة الإجازات، وهي إحدى نقاط الاحتكاك الأساسية التي حددها تقرير التدقيق.

أصبح مسار طلبات الإجازات يعتمد على التصفية الحقيقية من جانب الخادم، وترحيلاً متوافقاً مع كائن `Paginator`، وروابط وإجراءات Django الفعلية بدلاً من واجهة Ajax كانت تتوقع استجابات JSON من عروض تعيد عمليات توجيه. كما أُعيد تنظيم نموذج الإجازة إلى أقسام ذات تسميات ورسائل تحقق وحالة حفظ واضحة، مع الحفاظ على نموذج `EmployeeLeaveForm` والتحققات وقواعد البيانات القائمة.

| المجال | النتيجة | الأثر على المستخدم |
|---|---|---|
| النظام المرئي | الاعتماد على ملفات النظام الموحد والتحسينات الحرجة الموجودة في النسخة الأحدث | مظهر أكثر اتساقاً بين الصفحات الأساسية |
| طلبات الإجازات | جدول حديث مع تصفية، ترحيل، وحالات فارغة وإجراءات مرتبطة بالمسارات الفعلية | العثور على الطلبات ومراجعتها أسرع وأكثر وضوحاً |
| نموذج الإجازة | أقسام منطقية ورسائل خطأ مرتبطة بالحقول وحالة حفظ | تقليل أخطاء الإدخال ومنع الإرسال المكرر |
| الوصولية | تسميات للأزرار الأيقونية، عناوين جداول، مؤشرات تركيز، ودعم الحركة المخففة | تجربة أفضل لمستخدمي لوحة المفاتيح وقارئات الشاشة |

## شرح قبل وبعد

### قائمة طلبات الإجازات

قبل التحديث، كان القالب يعرض حالات وحقولاً لا تطابق نموذج `EmployeeLeave`، ويستخدم طلبات `fetch()` لتشغيل الإنشاء والاعتماد والرفض رغم أن العروض الفعلية تتطلب طلبات POST ثم تعيد التوجيه. كانت صفحة الترحيل أيضاً تنتظر متغيرات لا ينشئها العرض، كما كان رابط التصدير يضيف معاملاً لا يقرأه العرض.

بعد التحديث، تستخدم الواجهة كائن الصفحة `leaves` نفسه الذي يوفره العرض. أصبحت التصفية تشمل النص والموظف والنوع والحالة والتاريخ، وتُحفظ معايير البحث عند الانتقال بين الصفحات. ترتبط إجراءات العرض والتعديل بالمسارات المسماة، بينما تستخدم إجراءات الاعتماد والرفض نماذج POST مع رمز CSRF. يُظهر الجدول مدة الإجازة المحسوبة بواسطة الخاصية `duration_days` وقيم الحالة الفعلية (`Pending` و`Approved` و`Rejected` و`Cancelled`).

| المشكلة السابقة | التحسين المنفذ | أثر UX |
|---|---|---|
| فلتر الموظف ظاهر بلا بيانات أو دعم في العرض | تمرير الموظفين النشطين وتطبيق `emp_id` في العرض | تصفية موثوقة ومفهومة |
| أزرار Ajax تتوقع JSON من عروض تعيد توجيه | روابط ونماذج Django تقليدية وآمنة | الإجراءات تعمل دون أخطاء واجهة خفية |
| استخدام حالة بحروف صغيرة وحقول غير موجودة مثل `days` | استخدام خيارات النموذج و`duration_days` | شارات وأرقام صحيحة |
| حالة فارغة مجردة | حالة فارغة إرشادية مع إجراء إنشاء واضح | المستخدم يعرف الخطوة التالية |

### نموذج طلب الإجازة

قبل التحديث، كانت التنسيقات مضمنة في القالب ويُخفى حقل الحالة عند إنشاء طلب جديد، رغم كونه حقلاً مطلوباً في `EmployeeLeaveForm`. كما كانت رسائل الأخطاء منفصلة شكلياً عن عناصر الإدخال ولم يكن هناك تنظيم دلالي للحقول.

بعد التحديث، جُمعت الحقول في قسمَي بيانات الطلب وفترة الإجازة، ثم قسم للملاحظات والحالة. يحمل كل حقل مطلوب مؤشراً واضحاً، ورسالة خطأ مرتبطة بالحقل، ونص مساعدة عند توفره. تُرسل قيمة `Pending` المخفية للطلب الجديد، بينما تظل قائمة الحالة متاحة عند تعديل طلب قائم. يعطّل زر الحفظ بعد التحقق المحلي السليم ويعرض حالة تقدم لمنع الإرسال المكرر.

| المشكلة السابقة | التحسين المنفذ | أثر UX |
|---|---|---|
| احتمال فشل الطلب الجديد بسبب غياب حقل الحالة | إدراج قيمة `Pending` المخفية في الطلبات الجديدة | إرسال صالح ومتوافق مع النموذج |
| نموذج طويل بلا تقسيم دلالي | استخدام `fieldset` و`legend` للأقسام | قراءة أسرع ومسح بصري أفضل |
| مؤشرات خطأ غير متسقة | `is-invalid` و`invalid-feedback` لكل حقل | تحديد موضع الخطأ فوراً |
| غياب حالة منع الإرسال المكرر | زر حفظ مع `aria-busy` وحالة تحميل | تقليل الطلبات المتكررة |

## اعتبارات الوصولية والاستجابة

يعتمد التنفيذ على HTML دلالي ويضيف عناوين للجدول، و`scope` لرؤوس الأعمدة، و`aria-label` لأزرار الأيقونات، و`aria-current` لمسار التنقل. تُحافظ الجداول على التمرير الأفقي في الشاشات الضيقة من خلال `table-responsive`، بينما تصبح أزرار الرأس والنموذج بعرض كامل على الهاتف. توجد أيضاً مؤشرات تركيز مرئية ودعم لتفضيل المستخدم لتقليل الحركة.

> لم يُزل هذا التنفيذ أي صلاحية أو تحقق أو قاعدة عمل. صُممت التغييرات كتطوير تدريجي فوق `EmployeeLeaveForm` وعروض Django ومساراتها الموجودة.

## التحقق والجودة

تم تثبيت اعتماديات المشروع المعلنة ومحاولة تشغيل `python3 manage.py check`. وصل الفحص إلى تحميل إعدادات المشروع وتوقف عند اعتماد غير مذكور في `requirements.txt`: مكتبة `xlsxwriter` المطلوبة من `apps/reports/services.py`. لم ينتج هذا التوقف عن ملفات الواجهة أو وحدة الإجازات المعدّلة.

| التحقق | الحالة | الملاحظة |
|---|---|---|
| فحص اتساق العروض مع النموذج | مكتمل | تطابقت الحقول والحالات مع `EmployeeLeaveForm` و`EmployeeLeave`. |
| فحص المسارات والإجراءات | مكتمل | استُخدمت أسماء مسارات وحدة الإجازات ومسارات POST الفعلية. |
| مراجعة الوصولية في القوالب المعدلة | مكتمل | أضيفت تسميات وسياق دلالي ومؤشرات تركيز. |
| `python3 manage.py check` | متوقف بيئياً | يلزم إضافة `XlsxWriter` إلى متطلبات المشروع أو تثبيته في بيئة التطوير ثم إعادة التشغيل. |
| اختبار متصفح شامل | مطلوب بعد توفر قاعدة بيانات التطوير | يحتاج بيانات تسجيل دخول وقاعدة بيانات مهيأة. |

## الخطوات التالية المقترحة

يُوصى أولاً بإضافة `XlsxWriter` إلى `requirements.txt` وتشغيل `python3 manage.py check` مرة أخرى. بعد ذلك، ينبغي تشغيل الخادم ببيانات تطوير وإجراء اختبار يدوي لمسارات قائمة الإجازات والإنشاء والتعديل والاعتماد والرفض على شاشات بعروض 375 و768 و1024 بكسل. المرحلة التالية ذات الأولوية هي توحيد القالب الخاص بوحدة الإجازات مع القالب العام `templates/base.html` حتى تتشارك الوحدة ذاتها الشريط الجانبي ونظام الألوان ومعايير الوصولية لبقية المنصة.
